# writing-maestro 오케스트레이터 설계

> 2026-10-29 · 브레인스토밍 결과. 사용자가 정한 것과 설계자(Claude)가 정한 것을 구분해 적는다. 설계자 판단은 **[설계 판단]**으로 표시한다.

## 1. 의도

설치된 외부 글쓰기 스킬(v3 선정 58개 + 동반 9개)을 **스킬 레지스트리**에 기능·특징 요약과 함께 등록해 두고, `writing-maestro`를 호출하면 레지스트리에서 과제에 맞는 스킬을 골라 **여러 개를 조합해** 글 시안을 만든다.

가장 중요한 요구는 **조합된 스킬끼리 충돌하지 않는 것**이다. 여기서 충돌은 주로 *같은 측면을 서로 다르게 지시하는 스킬이 한 시안에 함께 들어가는 것*을 뜻한다(사용자 확인). 예: `general-writing`, `prose-naturalizer`, `humanizer`는 모두 문장 다듬기를 지시하지만 규칙이 다르다. `prose-naturalizer` 원문은 원고 집필 스킬과 같이 로드하면 지시가 충돌한다고 직접 적고 있다. 이를 막는 장치가 레지스트리의 클러스터링이다.

부차적 충돌: 같은 저장소 안에서 순서가 짜인 스킬 흐름(story-skills, social-media-skills 등)에 다른 스킬이 끼어들어 흐름이 깨지는 경우. 사용자 판단으로 드물지만 대비한다. 산출 파일 규약 차이(`voice.md` vs `voice/<name>.md`)는 조합 규칙에 메모 수준으로 다룬다.

선례: 같은 사용자의 `design-maestro`(`/Users/chan/Developer/Skills/Design-Skills/plugins/design-skills/skills/design-maestro/`). 레지스트리를 매 호출 새로 읽기, 배제 방식 선택, 허용 조합 표, 병렬 서브에이전트 시안, `feedback.md` 사이클을 이어받는다. 차이: design-maestro는 사용자에게 묻지 않고 옵션 3×시안 2로 고정이지만, writing-maestro는 조합과 시안 수를 **사용자에게 묻는다**.

## 2. 목표 · 비목표 · 반목표

**목표**
- 작문과 관련된 모든 과제를 다룬다(사용자 결정): **새 글 쓰기, 기존 글 고치기, 검토만 하기, 코드베이스 문서 작업**. 과제 종류별 경로는 §3.1.
- 호출 한 번으로: (필요하면 과제 명확화) → 조합 후보 제시 → 사용자가 조합·개수 선택 → 완성된 글 시안 N개.
- 레지스트리가 각 스킬이 *결과물의 어느 측면을 결정하는지*를 담고, 그 정보로 충돌 없는 조합만 후보로 낸다.
- 조합마다 왜 다른 대안인지 한 줄로 설명한다.

**비목표**
- 시안 순위·추천 (design-maestro와 같이 넘기고 멈춘다).
- 게시·발송·출판 등 글 이후의 행동.
- 런타임에 새 스킬 설치. 없는 스킬은 "설치 필요"로 보고만 한다.
- 서드파티 스킬 원문 수정.

**반목표 (기술적으로 돌아가도 실패로 본다)**
- 같은 측면을 결정하는 두 스킬이 한 시안의 조합에 함께 들어간다.
- 개수를 채우려고 사실상 같은 결과를 낼 조합을 따로 후보로 낸다.
- 사용자가 말하지 않은 품질 기준을 지어내 시안 지시에 넣는다.
- 질문이 여러 번 왔다 갔다 한다. 조합·개수 질문은 **한 번**으로 끝난다.

## 3. 사용자 여정

```
호출 ─▶ ① 과제 해석 ─▶ ② (필요 시) 명확화 단계 ─▶ ③ 조합 후보 산출
     ─▶ ④ 질문 1회: 조합 선택 + 조합당 시안 수 ─▶ ⑤ 병렬 시안 생성(+검수 단계)
     ─▶ ⑥ 결과 표 넘기고 멈춤 ─▶ (사용자가 평가하면) feedback.md 기록
```

1. **과제 해석.** "이 작업이 끝나면 어떤 글이 생기는가"로 장르·독자·분량·입력 자료·언어를 정한다. 레지스트리 범위 밖이면 이유만 보고하고 멈춘다.
2. **명확화 단계 (메인 대화에서).** 사용자와 대화가 필요한 스킬은 서브에이전트 안에서 쓸 수 없으므로, 조합을 제시하기 **전에** 오케스트레이터가 메인 대화에서 직접 쓴다(사용자 결정).
   - 대상: 레지스트리에서 `단계 = 명확화`로 표시된 스킬. 예: `interview-me`, `requirements-clarity`, `idea-refine`. 사용자 인터뷰나 샘플을 받아 지속 파일을 만드는 `brand-profile`, `voice-builder`, `awesome-content-voice`도 여기에 속한다 **[설계 판단]**.
   - 과제가 충분히 명확하거나 필요한 지속 파일(예: `brand-profile.md`)이 이미 있으면 건너뛴다 **[설계 판단]**.
   - 명확화로 만든 파일은 사용자 프로젝트에 두고, 이후 시안 서브에이전트가 읽는다.
3. **조합 후보 산출.** 레지스트리의 배제 규칙(§4.4)으로 후보를 만든다. 후보마다: 스킬과 순서, 다른 후보와 비교한 한 줄 차이. 후보는 최대 4개 **[설계 판단]**. 억지로 개수를 채우지 않는다.
4. **질문 1회** (사용자 결정). `AskUserQuestion` 한 번에 두 질문:
   - 어떤 조합으로 만들지 (복수 선택, 후보 목록)
   - 조합마다 시안을 몇 개 만들지 (모든 조합에 같은 수 **[설계 판단]**, 선택지 예: 1/2/3, 기타 입력 가능)
   - 적합한 조합이 하나뿐이면 첫 질문은 빼고 개수만 묻는다(사용자 결정).
5. **병렬 시안 생성.** 총 시안 수 = 선택 조합 수 × 조합당 수. 시안마다 서브에이전트 1개, 한 메시지에서 동시에 띄운다. 같은 조합의 시안끼리 차이를 강제하는 추가 지시는 **주지 않는다**(사용자 결정: 독립 실행만으로 달라진다). 서브에이전트 모델은 opus **[설계 판단, design-maestro 관례]**.
   - **검수 단계:** 레지스트리에서 `단계 = 검수`인 스킬(예: `citation-verification`, `docs-sync-audit`, `story-maintenance`의 `story check`, `build-evidence-map` 검증기)은 과제에 해당할 때 각 시안 서브에이전트가 초안 완성 **뒤** 마지막 단계로 적용한다(사용자 결정). 발견 사항은 고칠 수 있으면 고치고 NOTES.md에 기록한다 **[설계 판단]**.
6. **넘기기.** 결과 표(§6)를 넘기고 멈춘다.
7. **피드백.** 사용자가 시안을 평가하면 `feedback.md`에 사이클 기록과 사용자 기준을 더한다(design-maestro 방식). 레지스트리 수정 근거로 쓴다.

### 3.1 과제 종류별 경로
①에서 과제 종류를 넷 중 하나로 정한다(사용자 결정: 네 종류 모두 범위 안). 종류마다 다른 점만 적는다. 나머지는 위 여정과 같다.

| 종류 | 입력 | 시안이 뜻하는 것 | 다른 점 |
|---|---|---|---|
| 새 글 쓰기 | 요청, 자료 | 새로 쓴 글 | 기본 경로 |
| 기존 글 고치기 | 원문(파일·붙여넣기) | 원문을 고친 판본 (교정, 번역, 문체 변환, AI식 표현 제거 등) | 원문은 고치지 않는다. 각 시안이 자기 폴더에 원문을 복사해 작업. 시안 폴더에 원문 대비 변경 요약을 NOTES.md에 남긴다 **[설계 판단]** |
| 검토만 하기 | 검토 대상 | 검토 보고서 (발견 사항, 심각도, 수정 제안). 대상 원문은 고치지 않는다 | 후보는 검토 스킬(조합 가능). 조합 선택 질문은 하되, 같은 검토 스킬을 반복해도 얻는 것이 적으므로 **개수 질문은 하지 않고 조합당 1개** **[설계 판단]** |
| 코드베이스 문서 작업 | 레포의 문서 파일 (README, CLAUDE.md/AGENTS.md, 설계 문서 등) | 고친 문서 파일 묶음 | 시안끼리 레포를 덮어쓰지 않도록 각 시안은 대상 파일을 자기 시안 폴더로 복사해 작업한다. 레포 반영은 사용자가 시안을 고른 뒤 따로 한다 **[설계 판단]**. 읽기 전용 감사(`docs-sync-audit`)는 "검토만 하기"로 처리 |

### 3.2 질문할 수 없을 때 [설계 판단]
다른 에이전트가 부르거나 비대화형 실행처럼 `AskUserQuestion`을 쓸 수 없으면: 명확화 단계는 건너뛰고 스스로 정한 가정을 brief.md에 적는다. 조합 질문 대신 **모든 후보 조합 × 시안 1개**로 진행한다. 명확화 단계 스킬이 반드시 필요한 과제(예: brand-profile이 없는 소셜 콘텐츠)면 그 조합은 "실행 불가: 사용자 입력 필요"로 남긴다.

## 4. 레지스트리

### 4.1 위치와 형식 [설계 판단]
- `skills/writing-maestro/registry.md` (이 레포). 오케스트레이터가 매 호출 새로 읽는다. 사람이 읽고 고치는 문서이므로 Markdown.
- 앞부분: 범위, 측면(클러스터) 표, 단계 정의, 묶음 정의, 허용·금지 규칙. 뒷부분: 스킬별 항목.

| 필드 | 내용 |
|---|---|
| id / 이름 | 설치 디렉터리명 (예: `prompt-optimizer-sentry`) + `WM-X` id (동반 스킬은 없음) |

| **부 측면** | 본업은 아니지만 원문에 규칙이 있는 측면 (예: `copywriting`의 AI식 표현 금지 규칙). 조합에서 우선순위 지정 대상 (§4.3) |

| 실행 요건 | 필수(node, python, `story` CLI 등) / 선택(웹 검색 MCP, 네트워크, API 키) |
| 상태 파일 | 스킬이 만들거나 읽는 지속 파일 (`brand-profile.md`, `voice.md`, `story.md` …)과 위치 규약 |
| 주의 | 설치 검증에서 나온 제한 (`READY_WITH_LIMITS` 사유 등) |

### 4.3 클러스터 = 결정 측면 (충돌 방지의 핵심)
- 기존 연구의 58개 "기능 인접군"은 후보 압축용(기능 유사성)이라 충돌 판정에 맞지 않는다. 예: `general-writing`과 `prose-naturalizer`는 다른 인접군이지만 둘 다 문장 다듬기를 지시한다.
- 새 클러스터는 **"이 스킬이 결과물의 어느 측면을 결정하는가"** 기준으로 만든다. 한 스킬은 여러 측면을 결정할 수 있다.
- 대부분의 글쓰기 스킬이 본업 밖의 문장 규칙도 조금씩 갖고 있어서, 측면을 **주 측면**(본업)과 **부 측면**(곁가지 규칙)으로 나눈다. 충돌 규칙은 두 겹이다(사용자 결정: 주 측면 배제 + 우선순위 지정).
  1. **배제: 한 조합 안에서 주 측면이 겹치는 두 스킬은 함께 넣지 않는다**(묶음 예외 §4.5). 클러스터 = 같은 주 측면을 가진 스킬 묶음이고, 조합은 클러스터당 하나만 뽑는다.
  2. **우선순위: 한 스킬의 부 측면이 조합 안 다른 스킬의 주 측면과 겹치면, 그 측면은 주 측면을 가진 스킬을 따른다.** 오케스트레이터는 시안 지시에 "측면별 따를 스킬" 절을 넣어 명시한다. 예: "AI식 표현 제거는 `humanizer`를 따르고 `copywriting`의 같은 규칙은 적용하지 않는다." 부 측면끼리만 겹치고 주 측면 소유자가 없으면, 조합 순서상 뒤에 적용되는 스킬을 따른다 **[설계 판단]**.
- 우선순위 지정은 시안 지시 안에서만 한다. 서드파티 스킬 원문은 고치지 않는다.
- 측면 목록 초안 **[설계 판단, 빌더가 스킬 원문을 보고 확정·수정]**: 요구·의도 정의 / 근거·인용 / 전체 구조·논증 흐름 / 문장 문체·교정 / AI식 표현 제거 / 저자·브랜드 목소리 / 장르 규칙(학술·서사·마케팅·기술문서·소셜 등) / 포맷·채널 규격 / 독자 설득·전환 / 프롬프트 설계.
- 원문에 명시된 금지 짝은 측면 겹침과 무관하게 금지한다.

### 4.4 조합 후보 만들기 (배제 방식, design-maestro 계승)
1. 범위·장르가 과제와 다른 스킬을 지운다.
2. 단계가 명확화인 스킬은 조합에서 빼고 ② 단계로 보낸다. 검수 스킬은 조합 본체가 아니라 검수 단계로 붙인다.
3. 실행 요건 중 필수가 충족되지 않는 스킬은 지우고 "실행 불가"로 기록한다(선택 요건은 무시하고 진행).
4. 남은 스킬로 단계 순서(조사·근거 → 구조·초안 → 장르·포맷 → 문장·문체)를 따르는 조합을 만든다. 측면이 겹치는 스킬은 같은 조합에 넣지 않는다.
5. 조합의 생성 스킬은 최대 3개 **[설계 판단]**. 묶음 내부의 필수 동반은 이 수에 포함하지 않는다.
6. 후보끼리 "고유 접근" 차이를 한 줄로 쓸 수 없으면 하나만 남긴다.
7. 사용자가 스킬을 지명했으면 그 스킬이 들어간 조합을 첫 후보로 둔다.

### 4.5 묶음 (흐름 보호)
- 같은 저장소 안에서 서로 호출 순서가 정해진 스킬 집합. 초기 대상 **[설계 판단, 빌더가 원문으로 확인]**:
  - story-skills: `story-init`, `character-management`, `plot-structure`, `premise-workshop`, `scene-craft`, `chapter-writing`, `line-editing`, `verse-craft`, `story-maintenance` + 동반 `voice-style`, `theme-craft`, `genre-craft`, `submission`, `revision-continuity`
  - social-media-skills: `brand-profile`, `voice-builder`, `hook-writer`, `short-form-video-script`
  - msimchowitz writing-skills: `paper-writing`, `abstract-writing`, `academic-voice`, `general-writing`, `literature-review`, `non-autoregressive-writing-pass`, `prompt-improving` + 동반 `humanizer`, `better-usage`, `writing-cadence`
  - technical-writer: `technical-writing`(기반) + 문서 유형 스킬 5개
- 묶음 규칙: 묶음 스킬이 원문에서 부르는 같은 묶음 스킬은 측면이 겹쳐도 허용한다(원문이 순서를 조율하므로). 묶음 흐름 중간에 다른 묶음·독립 스킬을 같은 측면으로 끼워 넣지 않는다.

## 5. 레지스트리 구축 (구현 1단계)
- 입력: 설치된 SKILL.md(`~/.claude/skills/<name>/`, `doc-coauthoring`은 `anthropic-skills` 플러그인 사본), 설치 매니페스트, `research/selection/pruning_405_v3.json`.
- 설치 매니페스트(현재 세션 임시 폴더의 `install-manifest.json`)를 `research/install/2026-10-29-install-manifest.json`으로 레포에 옮겨 커밋한다.
- 스킬별 항목 작성은 병렬 에이전트로 나눈다(묶음 단위 배정). 측면 목록 확정과 충돌 판정은 전체를 보는 단일 패스로 한다. 측면은 원문의 지시 내용으로 판정하고, 각 판정에 원문 근거 한 줄을 남긴다.

## 6. 시안 생성과 출력

출력 폴더 **[설계 판단]**: `<프로젝트 루트>/writing-drafts/<YYYYMMDD-HHMM>-<과제-slug>/` (프로젝트가 없으면 현재 작업 폴더)
```
brief.md                         # 해석, 가정, 명확화 결과, 조합 후보와 선택, 제외 사유
combo1-<id>+<id>/d1/ d2/ …       # 시안별 폴더: 본문 파일 + NOTES.md
combo2-<id>+<id>/d1/ …
```
- 서브에이전트 지시에 포함: 과제 종류와 해석, 조합(스킬 순서와 SKILL.md 경로), 순차 적용 규칙(앞 스킬 산출물만 다음 스킬로), **측면별 따를 스킬**(§4.3의 우선순위 결과), 해당 검수 스킬, 원문·대상 파일 경로(고치기·문서 작업이면 복사해서 쓸 것), 명확화 산출 파일 경로, 품질 기준(이번 요청 + `feedback.md` 사용자 기준, 없으면 "주어진 기준 없음"), 쓰기 위치(자기 폴더 밖에 쓰지 않음, 스킬 상태 파일도 폴더 안), 질문하지 말고 끝까지 쓸 것.
- 상태 파일을 만드는 스킬(예: `story init`)은 시안 폴더 안에서 만든다. 명확화 단계에서 만든 지속 파일(`brand-profile.md` 등)은 읽기만 한다.
- NOTES.md: 무엇을 썼는지 3줄, 적용한 스킬과 순서, 검수 결과, 생략한 단계와 이유.
- 실패한 시안은 재시도하지 않고 사유를 기록한다.

넘기는 형식:
```
## 글 시안: <과제 한 줄>
해석: 장르 / 독자 / 분량 / 언어
명확화: <쓴 스킬과 산출 파일, 없으면 "생략">
가정: <스스로 정한 것, 한 줄씩>
출력 폴더: <절대 경로>

| 조합 | 스킬(순서) | 왜 다른 대안인가 | 시안 | 검수 |
|---|---|---|---|---|

제외: <주요 후보만, "스킬 - 이유">
실행 불가: <있으면>
```
순위·추천은 넣지 않는다.

## 7. 파일 배치와 설치 [설계 판단]
- `skills/writing-maestro/SKILL.md`, `registry.md`, `feedback.md` (이 레포)
- `~/.claude/skills/writing-maestro` → 위 폴더 심링크 (design-maestro와 같은 방식)
- 오케스트레이터 문서는 한국어(design-maestro 관례).

## 8. 제약
- 서드파티 스킬은 `~/.claude/skills/`에 이미 설치됨(2026-10-29). 원문은 수정하지 않는다.
- 일부 스킬은 조건부(`READY_WITH_LIMITS`): 웹 검색·학술 MCP, 네트워크, 선택 렌더러. 레지스트리 실행 요건에 반영한다.
- 한국어 작문 품질은 아직 검증하지 않았다. 대부분의 스킬 원문은 영어 기준이다.

## 9. 검증 [설계 판단]
- 레지스트리: 모든 설치 스킬이 항목을 가진다. 측면·금지 짝·필수 동반 판정마다 원문 근거가 있다.
- 오케스트레이터: 과제 종류 넷을 모두 포함하는 시험 과제로 호출한다. 예: 새 글(한국어 블로그 글, 단편 소설 장면, 논문 초록), 고치기(AI 티 나는 한국어 문단 교정), 검토(기술 설계 문서 검토), 문서 작업(이 레포 README 개선). 확인할 것:
  - 후보 조합에 주 측면 겹침이 없다.
  - 부 측면이 겹치는 조합의 시안 지시에 "측면별 따를 스킬" 절이 있다.
  - 질문이 1회다. 시안이 지정 수만큼 생긴다.
  - 원문·레포 파일이 바뀌지 않는다.
- 질문할 수 없는 경로(§3.2)도 1회 시험한다.
