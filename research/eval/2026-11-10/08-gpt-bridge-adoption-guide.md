### 조합 적합성
- 조합 3(writing-for-agents → writing-runbooks)은 이 과제에 맞았다. 독자가 에이전트이고 산출물이 설정 런북이라 앞 단계가 "완료 기준, 사람 단계 안내문, 핵심어 정의", 뒤 단계가 "위험 표시, 되돌리기, 증상 표"를 맡았다. 두 시안 모두 NOTES의 "측면별 스킬" 표대로 실제 결과에 반영되어 있다(완료 조건/완료 기준 문구, `[읽기]/[쓰기|바꿈]/[사람]` 범례, 단계별 되돌리기).
- 시안 지시(brief)와 결과의 어긋남: brief는 reviewing-technical-prose를 조합에서 뺐다("후보 수 상한 안에서 조합 4와 고유 접근이 겹쳐 뺌"). 그런데 d1·d2의 NOTES 모두 technical-writing 6단계가 부른다는 이유로 마지막 점검에 reviewing-technical-prose를 썼다. 제외 결정이 시안 작성 단계에서 뒤집혔다. 동반 스킬(companion) 규칙과 brief 제외 목록이 충돌한 사례로 보인다. 결과물 품질에 해는 없었으나 brief가 조합 기록으로 부정확하다.
- brief 해석 항목에 대한 어긋남은 없다(주 독자 = 도입 프로젝트 세션, 사람 단계 안내, 먼저 확인).

### 시안 간 차별성
- 뼈대는 쌍둥이에 가깝다. 같은 범례 4종, 같은 요약 순서, 같은 절 구성(확장 → Node → 등록 → 스킬 → URL → 북극성 → 확인 → 사용 → 실패 → bridge-check), 같은 출처 인용 상당수. 둘 다 같은 조합이고 시안 지시가 거의 같아 구조 선택지가 넓지 않았다.
- 실제로 다른 선택: (1) 점검 방식(d1 "도구 목록 + 링크 + 환경변수" 3단 확인 vs d2 P1~P5 번호 점검, hub.log 점검), (2) 근거 표기(d1 인라인 링크 30개 + 출처 표 vs d2 상대 경로 괄호 + 링크 0), (3) 범위(d1 비검수 질문 `build-message.sh`, CLAUDE.md 포인터가 §3 필수 갈래, §7 자동 스크립트 vs d2 Claude Code 설정 절, 포인터는 선택, 첫 요청 검증 단계), (4) 재연결(d1 `/mcp` vs d2 세션 재시작). 어느 쪽을 고르느냐가 "도입 세션이 얼마나 자동으로 움직이나 / 문서가 얼마나 짧으냐"의 실질 선택이 된다. 완전한 쌍둥이는 아니나 문장만 다른 쌍도 아니다. 차별성은 중간.

### writing-maestro 개선 후보
1. (추정, 1회 관찰) 조합 후보에서 제외한 스킬이 시안 단계에서 companion 규칙으로 다시 쓰인 사례. brief의 "제외" 항목과 시안 지시(이 폴더에서는 NOTES가 말한 "과제 지시: 동반 스킬은 원문대로 따른다")가 충돌했다. SKILL.md 시안 지시에 "brief 제외 목록의 스킬은 companion으로도 부르지 않는다, 또는 부르면 brief에 반영한다" 중 하나를 명시하면 기록과 실행이 맞는다.
2. (추정) 같은 조합 안 2개 시안이 구조까지 닮는 문제. 시안 지시가 "조합당 시안 수"만 정해 두고 시안 간 분기 축(예: 검증 중심 vs 압축 중심, 근거 표기 방식)을 정하지 않아 각 시안이 같은 최선 구조로 수렴했다. 시안 지시에 시안마다 달라야 할 축 1~2개를 적게 하면 차별성이 커진다.
3. (추정) compare.html 중심 산출물과 NOTES.md의 자기 감사 결과를 평가 입력으로 쓸 때, 시안 본문과 감사 결과가 분리되어 있다는 점은 좋았다(감사에서 고친 것이 본문에 반영). 개선 필요 없음. 단 d1처럼 감사 후에도 접두 같은 문구 수준 오차가 남으므로, 감사 시 "증상 문구는 소스 문자열을 그대로 대조" 항목을 시안 지시의 검수 체크리스트에 넣으면 d1의 누락을 잡을 수 있다(d2 감사는 이 항목을 잡았다).
4. (추정) 근거 없는 추론이 지시문이 될 위험(d2 §3 "떼고 쓴다"). 시안 지시에 "코드 규칙이 아닌 작성자 추론으로 행동 지시를 쓸 때는 [추론]으로 표시한다"를 넣으면 NOTES에만 남는 가정이 본문에서도 드러난다.
