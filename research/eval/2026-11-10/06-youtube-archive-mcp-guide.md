`final/guide.md`(23,933B)는 d2와 51줄 차이가 나고 d1과는 464줄 차이가 나서 d2 계열이다. 변경 요지: 첫 단락의 파이프라인 그림 서술을 "이 서버의 단계 흐름 그림은 아직 없다. 레포의 `docs/architecture.html`은 … 서버 도구는 나오지 않는다"로 바꾸고 일부 코드 블록을 번호 단계 밖으로 옮김. `final/guide.html`, `guide.min.html`은 렌더링본으로 보고 읽지 않았다. `compare.html`은 지시대로 보지 않았다.

## 프로젝트 평가

### 시안 간 순위
동률(27점). 근소하게 d2를 앞에 둔다. 근거: brief의 품질 기준 중 "가장 적은 수정으로 바로 낼 수 있는 원고"에 해당하는 C7과 분량 준수(C1)에서 d2가 한 점씩 높다. d1은 C6(구체성 5)와 C3(4)에서 한 점씩 높아 "출처와 사실 일치"(brief 품질 기준 4번)와 구체성 쪽 기준에서는 d1이 앞선다. 사용자가 둘 중 무엇을 더 중시하는지에 따라 뒤집히는 차이다. 둘 다 `_PROMPT`와 `get_frame_path` 서술이 어긋나 같은 한 줄을 고쳐야 한다.

### 사용 전 수정 목록

- d2: (1) `[기록]`의 구현 보고서 경로를 존재하는 파일로 바꾸거나 "확인 불가"로 낮추기. (2) `파이프라인 참조` 5단계 `get_frame_path`와 `서버 고치기` 5번의 범위(`_PROMPT`도) 정정. (3) 분량 축소(`검증 기록`, `파일 지도` 우선). (4) 첫 단락의 `youtube-archive-mcp-pipeline.html` 문구를 사용자 결정 뒤로 미루기. (5) `[실행함]`에 붙은 "커밋 `0549b9f`"를 작업 트리 기준임을 밝히기.

### 조합 적합성
- `writing-runbooks`와 필수 동반 `technical-writing`은 이 과제(순서가 있는 설치, 상태, 복구가 있는 가이드)와 맞았다. 두 시안 모두 `실행함/미실행` 표시, 되돌리기, 증상 우선 문제 해결 제목이 들어가 독자가 "지금 믿고 써도 되나"를 단계마다 판단한다. brief의 "검증하지 않은 것은 따로 적는다"와도 맞는다.
- 어긋남: (a) `writing-runbooks`의 위험 등급 태그와 맨 앞 TL;DR, 범례 위치 요구가 형식 참조의 절 순서와 충돌해 두 시안이 각각 임의로 절충했다(NOTES.md의 "스스로 정한 가정"). (b) brief의 "분량 10~17KB"가 두 시안 모두 초과로 이어졌다. 원인은 runbook 스킬의 단계별 확인 명령, 범례, 되돌리기 요구가 형식 참조 11절에 더해졌기 때문이다. (c) brief가 "측면별 우선 스킬 없음"인 상태에서 두 시안이 서로 다른 해석("한 사실 한 곳" 적용 정도)을 썼다.
- 두 시안 모두 NOTES.md의 자기 설명은 본문과 대체로 일치한다. 예외: d2 NOTES.md는 "guide.md에서 확인된 어긋남 0건"이라 했으나 본문 `파이프라인 참조` 5단계의 `_PROMPT` 귀속은 틀렸다(감사가 놓침). d1 NOTES.md는 `get_frame_path` 누락 범위를 고쳤다고 하면서 같은 문서의 파이프라인 단계는 고치지 못했다.

### 시안 간 차별성
부분적으로 다른 선택지다. 같은 형식 참조와 같은 스킬 조합이라 절 뼈대와 문체 규칙은 같지만, (1) 실행 표시 체계(2종 굵은 표시 vs 4종 태그), (2) 포함 범위(d1은 상태 절과 품질 동등성 실측 절을 더함, d2는 brew 부작용과 Windows 미지수를 더함), (3) 설정 예시(d1은 JSON 직접 설정, d2는 `pip install -e` + `claude mcp add`를 권장 경로로 둠. d1은 기록이 있는 경로를 권장, d2는 README 경로를 권장하고 기록 없음을 `[초안]`으로 표시)가 실질적으로 다르다. 권장 경로 선택이 실제 사용 판단에 영향을 주는 차이다. 문장 수준은 둘 다 같은 스킬에서 나와 비슷하다(오류 문구 제목, "원인: … 조치: …").
