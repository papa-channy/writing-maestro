# writing-maestro

과제를 레지스트리의 스킬 조합에 매핑하고(1~4절), 필요하면 과제를 명확히 하고(5절), 조합과 개수를 한 번 묻고(6절), 시안을 만들어 넘긴 뒤 멈춘다(7~8절). 고르는 방법은 점수가 아니라 배제다. 조합이 충돌하는지는 판단하지 않고 `combo_check.py`가 결정한다.

이 문서에서 쓰는 경로:
- `W` = 이 SKILL.md가 있는 폴더. 설치 경로는 `~/.claude/skills/writing-maestro`(레포 폴더로 가는 심링크)다. `registry.md`, `feedback.md`, `scripts/`가 여기 있다.
- 설치 매니페스트는 `registry_check.py`가 `W/registry.md`의 실제 경로(심링크를 푼 경로)에서 찾는다: 레포 루트의 `research/install/2026-10-29-install-manifest.json`. 따로 넘기지 않는다.
- 스킬 원문: `~/.claude/skills/<이름>/SKILL.md`. 예외로 `doc-coauthoring`은 플러그인 사본이라 `ls -d ~/.claude/skills/synced/*/doc-coauthoring`으로 찾는다(레지스트리 출처가 plugin).

## 고정 규칙
- 조합·개수 질문은 `AskUserQuestion` **한 번**이다. 다시 묻지 않는다. 명확화 스킬의 인터뷰(5절)는 그 스킬의 절차이고 이 질문과 별개다.
- 조합 후보는 최대 4개, 조합당 생성 스킬은 최대 3개다. 개수를 채우려고 사실상 같은 결과를 낼 조합을 넣지 않는다.
- 조합은 `combo_check.py --check-runtime`이 ok를 낸 것만 사용자에게 보인다. 실패한 조합을 다른 스킬로 바꿔 끼우지 않는다. 실패는 그대로 "제외"나 "실행 불가"에 적는다.
- 같은 조합의 시안끼리 서로 다르게 쓰라는 지시를 넣지 않는다. 독립 실행만으로 달라진다.
- 품질 기준은 사용자가 이번에 말했거나 `feedback.md` "사용자 기준"에 있을 때만 쓴다. 지어내지 않는다.
- 원문·대상 파일·레포 파일은 고치지 않는다. 시안은 자기 폴더에 복사해서 작업한다. 서드파티 스킬 원문도 고치지 않는다. 우선순위는 시안 지시 안에서만 정한다.
- 시안을 넘기면 멈춘다. 순위, 추천, 레포 반영, 게시·발송은 하지 않는다.
- 스킬에 관한 사실(항목 필드, 측면, 단계 값, 묶음, 조합 충돌 규칙)이 이 문서와 다르면 레지스트리를 따른다. 과제 종류별 경로와 실행 절차(검토 과제에서 검수 스킬을 조합 구성원으로 쓰는 것 포함)는 이 문서를 따른다.

# 매핑

## 1. 과제 해석
"이 작업이 끝나면 어떤 글이 생기는가"에 먼저 답한다. 그다음 다섯 가지를 정한다: 장르, 독자, 분량, 입력 자료(원문 파일·붙여넣은 글·레포 경로·자료), 언어. 요청과 컨텍스트(대화, 프로젝트 문서, 기존 `brand-profile.md`·`voice.md`·story 프로젝트)에서 근거를 찾는다.

과제 종류를 넷 중 하나로 정한다(레지스트리 `과제 종류` 값).

| 종류 | 신호 | 시안이 뜻하는 것 |
|---|---|---|
| `new` 새 글 쓰기 | 원문 없이 "써줘" | 새로 쓴 글 |
| `edit` 기존 글 고치기 | 원문이 있고 고친 판본을 원함(교정, 번역, 문체 변환, AI식 표현 제거) | 원문을 고친 판본 + 변경 요약 |
| `review` 검토만 하기 | 결과물이 평가뿐("검토해줘", "문제점만", 읽기 전용 감사) | 검토 보고서(발견 사항, 심각도, 수정 제안) |
| `docs` 코드베이스 문서 작업 | 레포 문서(README, CLAUDE.md/AGENTS.md, 설계 문서, 런북)를 쓰거나 고침 | 고친 문서 파일 묶음 |

- "검토하고 고쳐줘"는 `edit`(레포 문서면 `docs`)다. 결과물이 평가뿐일 때만 `review`다. 레포 문서의 읽기 전용 감사(`docs-sync-audit`)도 `review`다.
- 사용자가 스킬 이름을 직접 말했는지 적어 둔다(4절).
- 질문할 수 있는 실행인지 정한다. `AskUserQuestion`을 쓸 수 없는 환경이거나, 다른 에이전트가 불렀거나, "묻지 말고" 같은 비대화형 지시가 있으면 질문할 수 없는 실행이다(6절 끝).
- 출력 폴더 경로를 정한다: `<프로젝트 루트>/writing-drafts/<YYYYMMDD-HHMM>-<slug>/`. 프로젝트 루트는 `git rev-parse --show-toplevel`, 레포가 아니면 현재 작업 폴더다. 시각은 `date +%Y%m%d-%H%M`. slug는 소문자 ascii 케밥(a-z, 0-9, `-`), 40자 이내다. 한국어 과제는 짧은 영어 요지로 쓴다(예: "AI 글쓰기 도구 고르는 법 블로그 글" → `blog-choosing-ai-writing-tools`). 폴더는 처음 파일을 쓸 때 만든다(5절 명확화 산출이나 7절 brief.md).

## 2. 레지스트리 읽기
호출할 때마다 새로 읽는다. 기억이나 이전 호출 결과를 쓰지 않는다. `registry.md`는 크므로 통째로 읽지 않는다.
1. 검증: `python3 W/scripts/registry_check.py --registry W/registry.md`. 출력은 세 가지다.
   - exit 1(구조 오류 줄, `WARN `으로 시작하지 않는 줄)이나 exit 2(`ERROR ` 한 줄, 매니페스트·레지스트리를 못 읽음): 출력된 줄을 그대로 보고하고 멈춘다(8절의 레지스트리 실패 형식). 후보도 질문도 만들지 않는다.
   - exit 0이고 마지막 줄이 `OK <n> skills (<k> warnings)`: `WARN <스킬>: not installed (...)` 줄의 스킬은 "실행 불가: 설치 필요"로 다룬다. 후보에서 빼고 "실행 불가"에 `<스킬> - 설치 필요 (<괄호 안 사유>)`로 적는다. 구성원의 `필수 동반`(동반의 동반 포함)에 그 스킬이 있는 구성원도 같다. 지명 스킬이어도 바꿔 끼우지 않는다(4절 6번). 나머지는 그대로 진행한다. `WARN <스킬>: installed but not in registry`는 후보에 영향이 없다(brief.md에만 적는다).
   - exit 0이고 `OK <n> skills`: 그대로 진행한다.
2. 머리말: `awk '/^## 스킬/{exit} {print}' W/registry.md`. 범위, 측면, 단계, 묶음, 조합 규칙이 여기 있다.
3. 요약: `python3 W/scripts/registry_lookup.py --registry W/registry.md --summary`. 스킬마다 한 줄 `이름 | 주 측면 | 부 측면 | 단계 | 과제 종류 | 묶음 | 역할`. 줄 순서가 레지스트리 순서다.
4. 전체 항목은 후보로 남은 스킬만: `python3 W/scripts/registry_lookup.py --registry W/registry.md --skill <이름> ...`. 맞는 상황·맞지 않는 상황·고유 접근·필수 동반·실행 요건·상태 파일·주의를 여기서 본다. 없는 이름이면 exit 1이다.
5. `W/feedback.md`를 읽는다. "사용자 기준"은 7절 지시의 품질 기준에 넣는다. 이번 호출에서 사용자가 다르게 말하면 이번 말을 따른다. "스킬 관찰"은 후보를 지우는 근거가 아니다. 해당 스킬 시안 지시의 주의로만 넘긴다.

## 3. 범위 판정과 후보 풀
레지스트리 "범위" 절의 다룬다/다루지 않는다에 1절의 결과물을 대 본다.
- 전부 범위 밖(예: "엑셀 수식 짜줘", 코드 구현, 이미지 생성, 게시·발송): 명확화·후보·질문·서브에이전트 없이 8절의 범위 밖 형식으로 보고하고 멈춘다.
- 일부만 범위 안(예: "글 써서 메일로 보내줘"): 범위 안 부분만 과제로 삼는다. 나머지는 결과의 "범위 밖"에 적는다.

요약 줄을 단계로 먼저 나누고, 무리마다 거른다.
- **명확화 전용**(단계가 `clarify`뿐): 조합에 넣지 않는다. 5절에서 필요할 때만 쓴다.
- **검수 전용**(단계가 `check`뿐):
  - `new`·`edit`·`docs`면 과제 종류로 거르지 않는다. 전체 항목을 읽고, 이번 결과물이 그 스킬이 점검하는 대상일 때만 검수 단계 후보로 둔다(참고문헌이 있는 글 → `citation-verification`, 코드와 맞물린 레포 문서 → `docs-sync-audit`, story 프로젝트 → `story-maintenance`). 조합 구성원이 아니다.
  - `review`면 아래 구성원 후보와 같이 걸러 조합 구성원 후보로 둔다.
- **나머지**(`check`와 다른 단계를 함께 가진 스킬 포함)는 다음 순서로 거른다.
  1. `과제 종류`에 1절의 종류가 없는 스킬을 지운다.
  2. 역할이 장르·독자·결과물과 다른 스킬을 지운다(예: 블로그 글에 소설 스킬, 한국어 README에 학술 초록 스킬).
  3. 남은 스킬의 전체 항목을 읽고 "맞지 않는 상황"에 걸리는 스킬을 지운다.
  남은 것이 조합 구성원 후보다.

## 4. 조합 후보
1. 필수 명령이 없는 스킬은 쓸 수 없다. 아래 검증의 `--check-runtime`이 `missing_commands`로 잡는다. 선택 요건(웹 검색 MCP, 네트워크, API 키)은 없어도 진행하고 그 단계를 생략한다.
2. 구성원 후보로 조합을 만든다. 같은 주 측면을 가진 스킬(같은 클러스터)은 한 조합에 하나만 넣는다. 단독 스킬도 조합이다.
3. 조합 안 순서: 단계 순서 research → draft → genre → prose → check로 놓는다. 단계가 여럿인 스킬은 `clarify`가 아닌 첫 단계 자리에 놓는다(예: `literature-review` research, `reviewing-technical-prose` check·prose → prose). 같은 자리끼리는 요약 줄 순서를 따른다. 이 순서가 시안의 적용 순서이고, `combo_check.py`에 넘기는 순서이고, 폴더 이름의 순서다. `review` 조합도 같은 규칙으로 정한다.
4. 생성 스킬은 조합당 최대 3개다.
5. 후보끼리 "고유 접근" 차이를 다른 후보와 비교한 한 줄로 쓸 수 없으면 하나만 남긴다. 후보는 최대 4개다.
6. 사용자가 등록된 스킬을 지명했으면 그 스킬이 든 조합을 후보 1로 둔다. 지명 스킬은 3절의 거르기를 건너뛴다(과제 종류에 없으면 "가정"에 적는다). 범위 판정과 `combo_check.py`는 그대로 받는다. 지명 스킬이 명확화 전용이면 5절에서, 검수 전용이면 검수 단계나 `review` 조합 구성원으로 쓴다.
7. 요약 줄에 없는 이름을 지명했으면 쓰지 않고 "제외"에 `<이름> - 미등록`으로 적는다. 비슷한 등록 스킬로 바꾸지 않는다. 나머지 후보는 그대로 만든다.

조합에는 오케스트레이터가 직접 순서를 짜는 스킬만 넣는다. 구성원이 원문에서 스스로 부르는 `필수 동반`과 그 동반의 동반(예: `general-writing` → `humanizer` → `writing-cadence`, `writing-design-docs` → `technical-writing`)은 구성원으로 넣지 않는다. 시안 서브에이전트가 구성원 SKILL.md를 따르면 동반 스킬이 따라 들어오고, `combo_check.py`가 그 닫힘까지 충돌을 따진다.

검증: 후보마다 실행한다. 검수 단계 스킬과 명확화 전용 스킬은 넘기지 않는다(`review`면 검토 스킬 전부가 구성원이다).
```
python3 W/scripts/combo_check.py --registry W/registry.md --check-runtime <스킬1> [<스킬2> <스킬3>]
```
- exit 0이고 `"ok": true`인 후보만 남긴다. JSON의 `precedence`와 `ignored`는 7절 지시에 그대로 쓰므로 후보별로 보관한다.
- `conflicts`가 있으면 "제외"에 `<조합> - <충돌 문자열>`(예: `general-writing+prose-naturalizer - primary overlap ai-tells: general-writing, prose-naturalizer`)로 적는다.
- `missing_commands`만 있으면 "실행 불가"에 `<조합> - <skill:cmd> 없음`으로 적는다.
- 지명 스킬이 든 조합이 실패해도 같다. 실패를 보고하고, 지명 스킬을 빼거나 바꾼 조합을 몰래 만들지 않는다. 지명 스킬 없이 나머지로 만든 후보는 같은 규칙대로 낼 수 있다.
- 검수 단계 후보도 실행 요건을 따로 확인한다: `python3 W/scripts/combo_check.py --registry W/registry.md --check-runtime <검수 스킬>`(검수 스킬 하나만 넘긴다). 실패하면 검수 단계에서 빼고 "실행 불가"에 적는다.

남은 후보가 없으면 명확화도 질문도 하지 않고 8절 형식으로 "제외"와 "실행 불가"만 보고하고 멈춘다.

## 5. 명확화 단계 (메인 대화에서)
사용자와 대화가 필요한 스킬은 서브에이전트 안에서 쓸 수 없다. 그래서 검증을 통과한 후보가 정해진 뒤, 질문(6절) **전에** 여기서 직접 쓴다. 질문할 수 없는 실행이면 이 절을 건너뛰고 6절 끝을 따른다.

남은 후보에 필요한 지속 파일은 다음처럼 다룬다. 질문할 수 있든 없든 같은 규칙이다.

| 파일 | 필요한 후보 | 없을 때 (질문 가능) | 없을 때 (질문 불가) |
|---|---|---|---|
| `brand-profile.md` (`brand-profile`) | `hook-writer`, `short-form-video-script` 등 필수 동반에 `brand-profile`이 있는 후보 | 여기서 `brand-profile`로 만든다 | 그 후보는 "실행 불가: 사용자 입력 필요" |
| `voice.md` (`voice-builder`) | 필수 동반에 `voice-builder`가 있는 후보 | 사용자가 실제 글 샘플을 줬으면 여기서 `voice-builder`로 만든다. 샘플이 없으면 만들지 않고 voice.md 없이 진행한다 | voice.md 없이 진행하고 "가정"에 적는다 |
| story 프로젝트 (`story-init`) | story 묶음 후보 | 기존 프로젝트가 없으면 `story-init`이 묻는 항목(제목·형식·장르·시점·시제·언어 등)만 받아 `<출력 폴더>/clarify/story-init.md`에 적는다 | 그 항목을 스스로 정해 brief.md "가정"에 적는다 |

- 이미 있는 최신 `brand-profile.md`로 재인터뷰하지 않는다. 기존 story 프로젝트가 있으면 story-init을 쓰지 않는다.
- story 프로젝트는 여기서 만들지 않는다. 시안 스킬이 그 안에 고쳐 쓰므로 각 시안이 자기 폴더 안에서 `story init`을 하거나 기존 프로젝트를 복사한다(7절).
- 의도 명확화: 1절의 다섯 가지 중 결과가 크게 갈리는 것(목적, 독자, 성공 기준)을 요청과 컨텍스트로 정할 수 없을 때만, 맞는 상황이 가장 가까운 의도 스킬 하나(`interview-me`, `requirements-clarity`, `idea-refine`, `doc-coauthoring`의 컨텍스트 수집 등)를 쓴다. 답으로 1절 해석(과제 종류·장르·독자)이 바뀌면 3~4절을 새 해석으로 한 번 다시 한다(질문 없이, `combo_check.py` 다시 실행).
- 쓰는 법: 스킬 SKILL.md를 읽고 사용자 답이 필요한 부분까지만 그 절차대로 진행한다. 본문 시안은 여기서 쓰지 않는다. 필수 명령이 있는 명확화 스킬은 먼저 `command -v <명령>`으로 확인하고, 없으면 그 스킬이 필요한 후보를 "실행 불가: <명령> 없음"으로 뺀다.
- 산출 위치: 스킬이 위치를 정한 지속 파일(`brand-profile.md`, `voice.md`, `voice/<name>.md`)은 스킬 규약대로 사용자 프로젝트에 둔다. 시안은 읽기만 한다. 두 보이스 규약(`voice.md`와 `voice/<name>.md`)은 한 시안에서 하나만 쓴다. 위치가 정해지지 않은 결과(의도 진술문, PRD, 아이디어 한 장, story-init 항목)는 `<출력 폴더>/clarify/<스킬>.md`에 둔다.
- 명확화에서 쓴 스킬과 산출 파일은 brief.md와 결과의 "명확화" 줄에 적는다. 명확화 뒤 남은 후보가 없으면 8절 형식으로 보고하고 멈춘다.

## 6. 질문 1회
`AskUserQuestion`을 한 번 호출한다. 질문은 최대 두 개다.
- 질문 1 (header `조합`, multiSelect true): "어떤 조합으로 시안을 만들까요? (여러 개 선택 가능)". 선택지마다 label `조합 k: <스킬1> → <스킬2>`, description은 "왜 다른 대안인가" 한 줄(+ 검수 단계가 붙으면 `검수: <스킬>`).
- 질문 2 (header `시안 수`, multiSelect false): "조합마다 시안을 몇 개 만들까요? 모든 조합에 같은 수로 만듭니다. 총합으로 정하려면 기타에 '총 N개'로 적어 주세요." 선택지 `1개`, `2개`, `3개`(기타 입력은 도구가 붙인다).

빼는 경우:
- 후보가 하나면 질문 1을 빼고 질문 2만 묻는다.
- `review`면 질문 2를 빼고 조합당 1개다. `review`이고 후보도 하나면 묻지 않고 바로 7절로 간다.

답 해석(다시 묻지 않는다):
- 숫자만 오면 조합당 개수다. "총 N개", "전체 N개", "합쳐서 N개"면 총합이다. 총합은 고른 조합 수 k로 나눠 각 조합에 N÷k(몫)개, 나머지 N mod k개는 앞 조합부터 1개씩 더 준다(총 5개, 2조합 → 3, 2). N이 k보다 작으면 앞 조합부터 1개씩 주고 0개인 조합은 표에 "만들지 않음(총 N개 배분)"으로 적는다.
- 기타에 조합까지 적은 자유 답("2번만 2개씩")은 그 말대로 따른다. 해석할 수 없는 부분은 모든 선택 조합 × 1개로 정하고 "가정"에 적는다.
- 조합을 하나도 고르지 않았으면 모든 후보를 고른 것으로 본다.

질문할 수 없을 때(1절에서 정한 경우):
- 5절 명확화는 건너뛴다. 지속 파일은 5절 표의 "질문 불가" 칸대로 한다. 스스로 정한 해석과 항목은 brief.md "가정"에 적는다.
- 나머지 **모든 후보 조합 × 시안 1개**로 진행한다.

# 시안 생성

## 7. 시안 생성
출력 폴더(1절에서 정한 경로):
```
brief.md                          # 해석, 가정, 명확화 결과, 조합 후보와 선택, combo_check 결과 요약, 제외·실행 불가 사유
source/original.md                # 붙여넣은 원문이 있으면 그 사본 (파일 원문은 원래 경로를 쓴다)
clarify/                          # 5절 산출 파일 (있을 때)
combo1-<스킬>+<스킬>/d1/ d2/ …     # 시안별 폴더: 본문 파일 + NOTES.md
combo2-<스킬>/d1/ …
```
- brief.md는 서브에이전트를 띄우기 **직전에** 쓴다. 범위 밖, 레지스트리 검증 실패, 남은 후보 없음으로 멈출 때는 출력 폴더를 새로 만들지 않고 brief.md도 쓰지 않는다. 명확화 산출로 출력 폴더가 이미 있는데 후보가 없어져 멈추면 그때는 brief.md를 쓴다.
- 조합 번호 k는 질문에 보인 후보 번호를 그대로 쓴다. 폴더 이름의 스킬은 4절 3번 순서대로 `+`로 잇는다.
- 서브에이전트는 시안 하나에 하나. 총 수 = 고른 조합마다 정한 개수의 합. 전부 **한 메시지에서 동시에** 띄우고 model은 `opus`로 한다.
- 검수 단계: 3절에서 검수 단계 후보로 두고 4절 실행 확인을 통과한 스킬을 각 시안 지시에 넣는다. 초안을 끝낸 뒤 마지막 단계로 적용한다. `review`에는 붙이지 않는다.
- "측면별 따를 스킬": 그 조합의 `combo_check.py` JSON에서 만든다. `precedence`는 `{측면: 따를 스킬}`이고, `ignored`는 `[스킬, 측면]` 쌍의 목록이다(그 스킬의 그 측면 규칙이 밀려났다는 뜻). `ignored`에 나오는 측면마다 한 줄 `- <측면 id>(<측면 이름>): <스킬>을 따른다. <무시 스킬>의 <측면 id> 규칙은 적용하지 않는다.`를 쓴다(<스킬>은 `precedence`에서 찾는다). 한 측면에 무시 스킬이 여럿이면 `ignored` 순서대로 한 줄에 모은다: `A의, B의 <측면 id> 규칙은 적용하지 않는다.` `precedence`에만 있고 `ignored`에 없는 측면(조합 스킬 하나만 다루는 측면)은 쓰지 않는다. 예: `- ai-tells(AI식 표현 제거): humanizer를 따른다. copywriting의 ai-tells 규칙은 적용하지 않는다.`, `- evidence(근거·출처): build-evidence-map을 따른다. abstract-writing의, academic-voice의 evidence 규칙은 적용하지 않는다.` 해당하는 측면이 없으면 "없음".
- `review` 보고서 형식 스킬: 2절 요약 줄의 주 측면·부 측면 칸에 `review-report`가 있는 조합 구성원을 센다. 하나면 그 스킬이다. 둘 이상이면 "측면별 따를 스킬"의 review-report 줄의 스킬이고, 그 줄이 없으면(한 구성원이 review-report를 주 측면으로 가져 밀려난 스킬이 없을 때) 그 주 측면 소유 구성원이다. 없으면 형식 스킬 없이 스킬별 절로 나눈다.
- 스킬 SKILL.md 경로는 직접 확인해서 넣는다(`test -f ~/.claude/skills/<이름>/SKILL.md`, `doc-coauthoring`은 위 `ls -d`). 없으면 설치하지 않고 그 조합을 "실행 불가: 설치 필요 (<레지스트리 출처>)"로 돌린다.

서브에이전트 지시(시안마다 채워서 그대로 보낸다):
```
너는 글 시안 하나를 만든다. 질문하지 말고 끝까지 쓴다.
과제 종류: <new/edit/review/docs>
과제: <1절 해석: 결과물, 장르, 독자, 분량, 언어. 범위 안 부분만>
조합(적용 순서):
  1. <스킬1> — SKILL.md: <경로>
  2. <스킬2> — SKILL.md: <경로>
각 SKILL.md를 먼저 읽고 그 절차를 따른다.
<new·edit·docs: 앞 스킬을 끝까지 적용한 뒤 그 산출물만 들고 다음 스킬을 적용한다.>
<review: 각 스킬을 검토 대상 원문에 각각 적용한다. 앞 스킬의 보고서를 다음 스킬의 입력으로 쓰지 않는다. 발견 사항을 review.md 하나로 합친다. 형식 스킬이 있으면: 보고서 형식(판정·심각도 체계와 구조)은 <형식 스킬>의 보고서 형식을 따른다. 형식 스킬이 없으면: 스킬별 절로 나눈다.>
스킬 원문이 다른 스킬(동반 스킬)을 읽거나 적용하라고 하면 원문대로 따른다. 동반 스킬도 ~/.claude/skills/<이름>/SKILL.md에 있다.
측면별 따를 스킬 (같은 측면을 여러 스킬이 지시하면 아래만 따른다):
<4절 combo_check precedence/ignored에서 만든 줄들, 없으면 "없음">
검수 단계: <스킬 — SKILL.md 경로. 초안을 끝낸 뒤 마지막으로 적용한다. 고칠 수 있는 발견은 고치고 전부 NOTES.md에 적는다. 없으면 "없음">
원문·대상 파일: <경로 또는 "없음">. 원본은 고치지 않는다. 필요한 파일을 쓰기 위치로 복사해 그 사본에서 작업한다.
명확화 산출: <파일 경로와 한 줄 설명, 없으면 "없음">. 지속 파일(brand-profile.md, voice.md)은 읽기만 한다. <voice.md 없이 진행하면: voice.md는 없다. 보이스는 brand-profile.md만 따른다.>
<story 프로젝트가 필요하면 셋 중 하나: <출력 폴더>/clarify/story-init.md의 항목으로 / 질문 불가 실행이면 <brief.md 경로>의 "가정"에 적힌 항목으로 — 쓰기 위치 안에서 story init을 실행한다 / 기존 프로젝트 <경로>를 쓰기 위치로 복사해 쓴다>
품질 기준: <이번 요청과 feedback.md "사용자 기준"에서 온 기준. 없으면 "주어진 기준 없음">
주의: <레지스트리 "주의"와 feedback.md "스킬 관찰" 중 이 조합에 해당하는 것. 없으면 생략>
스킬 절차가 사용자 확인·승인·선택을 요구하면 스스로 정하고 그 결정을 NOTES.md에 가정으로 적는다.
비용: 상한 없음. 스킬 절차의 검사·감사 단계를 비용 때문에 생략하지 않는다. 생략은 필수 요건이 없을 때만 한다.
쓰기 위치: <시안 폴더 절대 경로>. 이 폴더 밖에는 아무것도 쓰지 않는다. 스킬이 만드는 상태 파일도 이 폴더 안에 둔다.
설치·다운로드·게시·발송은 하지 않는다.
결과물: <new: 본문 파일(예: draft.md) / edit·docs: 원래 파일 이름의 고친 사본 / review: review.md (발견 사항, 심각도, 수정 제안. 대상은 고치지 않는다)>
끝나면 쓰기 위치에 NOTES.md: 무엇을 썼는지 3줄, 적용한 스킬과 순서(동반 스킬 포함), 측면별로 실제 따른 스킬, 검수 결과, 생략한 단계와 이유, 스스로 정한 가정. edit·docs면 원문 대비 변경 요약도.
```
- 같은 조합의 d1, d2 … 에는 같은 지시를 보낸다. 쓰기 위치만 다르다.
- 실패한 시안은 다시 돌리지 않고 실패 이유를 결과에 적는다.

## 8. 넘기는 형식
아래 형식으로 넘기고 멈춘다. 순위, 추천, 다음 단계 제안은 넣지 않는다.
```
## 글 시안: <과제 한 줄>
해석: <과제 종류> / 장르 / 독자 / 분량 / 언어
명확화: <쓴 스킬과 산출 파일, 없으면 "생략">
가정: <스스로 정한 것, 한 줄씩. 없으면 "없음">
범위 밖: <제외한 부분과 이유. 없으면 생략>
출력 폴더: <절대 경로>
gitignore: <프로젝트 루트가 git 레포이고 `git -C <프로젝트 루트> check-ignore -q writing-drafts`가 실패하면(무시되지 않음) "writing-drafts/를 프로젝트 .gitignore에 더하면 시안이 커밋되지 않습니다." 레포가 아니거나 이미 무시되면 이 줄을 뺀다>

| 조합 | 스킬(순서) | 왜 다른 대안인가 | 시안 | 검수 |
|---|---|---|---|---|
| 1 | <스킬1> → <스킬2> | <다른 조합과 비교한 한 줄> | <d1 경로>, <d2 경로 또는 실패: 이유> | <검수 스킬: 결과 한 줄 / 없음> |

제외: <주요 후보만, "스킬 또는 조합 - 이유"(충돌 문자열, 미등록, 맞지 않는 상황)>
실행 불가: <"조합 - 이유"(skill:cmd 없음, 사용자 입력 필요, 설치 필요). 없으면 생략>
```
- `gitignore` 줄은 위 "다음 단계 제안 금지"의 예외다. 레포 파일(.gitignore 포함)은 고치지 않고 제안만 한다.
- 범위 밖이면 `해석`과 `범위 밖: <이유 한 줄>` 두 줄만 쓴다.
- 레지스트리 검증이 실패했으면 `레지스트리 검증 실패:`와 그 아래 오류 줄만 쓴다.
- 남은 후보가 없으면 표와 `출력 폴더` 줄을 빼고 `제외`·`실행 불가`를 쓴다(5절에서 출력 폴더를 만들었으면 `출력 폴더` 줄은 남긴다).
- `review`면 시안 칸에 `review.md` 경로를 쓴다.
- 사용자가 고르지 않은 후보는 표에 넣지 않고 brief.md에만 남긴다.

## 평가를 받은 뒤
사용자가 시안을 평가하면 `W/feedback.md` "사이클 기록"에 한 절을 더한다: 날짜·과제 한 줄, 표(시안, 평가, 사용자 말), 스킬 관찰. 사용자가 새로 말한 품질 기준은 "사용자 기준"에 더한다. 사용자가 말하지 않은 기준은 지어서 적지 않는다. 레지스트리를 고칠 근거가 보이면 제안만 하고, 고칠 때는 `registry.md` 머리말의 "고치는 법"을 따른다.
